# 공급계약 질문 평가 v2

현재 검색·필드 추출이 실제 질문에서 어디까지 동작하는지 측정하는 **개발용 회귀 평가**다.
9개 회사·12개 원본 공시를 바탕으로 만든 40문항이며, 독립적인 미공개 시험셋이나
일반 공시 QA의 품질 보증이 아니다. 원래 v1 질문셋과 사용자 실행 결과는 보존한다.

## v1 실측 결과와 v2 변경 이유

사용자가 실행한 `contract-qa-v1.json`은 40문항 완료, 26문항 통과였다.
정답 공시 hit@5는 25/32, 찾은 정답 공시에서 채점한 필드 71항목의 값·근거는 모두 일치했다.
문항별 측정시간 합계는 17.406초, 중앙값 0.297초, 95백분위 1.047초였다.
사전 검사·리포트 저장 등은 이 문항별 시간에 포함되지 않는다. API 40회, 오류/재시도 0회였다.
필드 정확도는 검색 성공 조건부 수치이며 전체 QA 정확도를 뜻하지 않는다.

v2는 P3 질문에 `장거리지대공유도무기-II` 사업명만 추가한다. 기존의
`체계종합 시제 사업`에는 실제로 다른 계약도 해당하므로 단일 정답을 강제하기 어려웠다.
원본 정답·필드·채점 조건과 나머지 39문항은 바꾸지 않았다. 변경 내역은 JSON의 `changes`에 남긴다.
기존 v1의 26/40을 사후에 올려 쓰지 않는다. 두 버전의 전체 점수는 완전히 같은 질문의 비교가 아니다.
새 리포트의 `comparison.unchanged_questions`는 P3를 제외한 39문항을 따로 집계한다.
이 39문항의 v1 통과 수는 26이었다. P3는 새 질문으로 별도 해석한다.

**현재 코드의 실제 v2 검색 성능은 아직 측정 전이다.** 단위 테스트의 통과를
사용자 PostgreSQL/검색 평가의 통과로 대신하지 않는다.

## 고정 범위

- Chunk run: `c700b5a3a6cfa055be147bc71dd478ca`
- Embedding run: `1220f708cc241e9a00d0b40cbddea7da` (`retrieval-embedding-v2`)
- 기존 178,822개 벡터 재사용. 청킹·문서 임베딩·인덱스 변경 없음.
- 기존 CLI와 같은 dense 검색: top-k 5, candidates 100, 공시당 최대 1개.
- 같은 `resolve_company`, `plan_contract_query`, `retrieve`, `contract_findings`를 호출한다.
- 계약 모드에서 공급계약 subtype + exchange + table로 범위를 제한한다.
- 명시한 수량(아라비아 숫자 + 대/척)은 쉼표·공백을 정규화한 별도 후보 검색으로 보완한다.
  수량이 정확히 같은 후보를 먼저 배치하고 그 안에서 기존 RRF 순위를 사용한다.
  수량 후보가 없어도 회사·날짜·공시 유형 조건을 완화하지 않는다.
- 기본 사실 12, 회사·기간 8, 표현 변형 8, 결측/빈 범위 6, 미지원 6.

## 정답을 만드는 방법

[벤치마크 v2 JSON](../data/benchmarks/supply-contract-qa-v2.json)의 정답은
커밋 `1a41d3edad033352774a157a5ab2321c29257803`의 원본 XML 12건에서
계약상대방·원화 금액·시작일·종료일 48개를 직접 읽어 작성했다.
검색 결과나 운영 추출기의 결과를 정답으로 복사하지 않았다.
별도의 외부 검수자가 검토했다는 의미는 아니다.

각 정답은 원본 경로, Git blob SHA, 내용 SHA-256, 값 셀의 XPath, 원문 텍스트,
정규화한 값, 상태, 단위를 포함한다. 로컬 검증은 운영 파서/추출기 대신
독립된 XML XPath 읽기로 이 정답이 원문과 같은지만 검사하며, 정답을 자동 수정하지 않는다.
체크아웃 호환성을 위해 내용 해시는 CRLF를 LF로 바꾸고 끝의 개행만 제거한다.

정답은 고정 공시의 **그 버전에 기재된 값**이다. 최신 정정본·유효 계약·현재 시점의
금액이라고 주장하지 않는다. 특히 LS 정정본은 해당 접수번호 자체를 대상으로 한다.
HMM의 상대방 원문 `-`는 `missing/null`이며 다른 공시로 채우면 오답이다.
한미반도체 자율공시도 포함한다. 사용자 v1 실행에서 이 원본은 지원 subtype으로 분류되어 통과했다.

## 평가 흐름과 채점

1. 40개 질문과 12개 원본/48개 정답을 로컬에서 검증한다.
2. 실제 실행은 완료된 고정 run 및 원본 적재 run을 읽기 전용으로 확인한다.
   12개 대상 공시의 존재·날짜·정정 여부·유효한 벡터 연결을 확인한다.
   대상이 빠졌으면 `corpus_errors`를 남기고 API 호출 전에 중단한다.
   1900년 빈 범위 2문항은 DB의 원본 공시에도 해당 범위의 자료가 없는지 확인한다.
3. **질문과 명시적 UI 옵션만** 검색에 넘긴다. 정답 접수번호·정답 날짜로 검색을 좁히지 않는다.
4. 상위 5개에 허용된 원본 공시가 있는지 확인한다. 특정 chunk ID 하나를 강제하지 않는다.
5. 찾은 대상 공시에서 요청된 필드의 값·상태·단위와 원본 셀/공시 링크를 비교한다.
   동일 대상의 중복 결과 중 맞는 것만 골라 틀린 결과를 숨기지 않는다.
6. 회사 혼입, 날짜 범위 미적용, 잘못된 근거, 미지원 질문의 거절 누락을 별도로 기록한다.

실패 분류: `retrieval_miss`, `extraction_missing`,
`field_value_status_or_unit_error`, `evidence_error`,
`wrong_company_result`, `company_scope_not_applied`,
`date_scope_not_applied`, `wrong_receipt_date_result`,
`unexpected_result_in_empty_scope`, `unsupported_intent_not_rejected`, `execution_error`.

`retrieval_hit_at_5`는 답변 가능한 32문항의 대상 공시 hit율이다.
`field_accuracy_conditional`과 `evidence_accuracy_conditional`은
**실제로 찾은 대상에 한정**되므로, 검색 실패를 제외한 이 값만으로 품질을 판단하면 안 된다.
분모, 그룹별 통과 수, 실패 분류, 전체 문항 통과 수를 함께 출력한다.
서로 관련된 40문항이므로 통계적 일반화 수치로 쓰지 않는다.

이것은 아직 자연어 최종 답변을 생성·채점하는 E2E 시험이 아니다.
top-5 대상 공시/요청 필드와 특정 범위 제약을 평가하며, 다른 반환 공시의 모든 필드까지
완전 채점하는 것도 아니다. 향후 답변 선택·생성 단계에는 별도 근거 충실성 평가가 필요하다.

### 질문 해석의 범위와 남은 한계

- 날짜 UI 옵션 4문항과 자연어 날짜 4문항은 분리한다. 이제 공통 질문 해석기를 통해
  연도/연월/연월일, `YYYY-MM-DD`·슬래시·점 구분 날짜 및 명확한 두 날짜 범위를 지원한다.
  별도 날짜 역할이 없는 연월일은 **공시 접수일로 해석했다는 안내**를 결과에 남긴다.
  계약 시작·종료·체결일 조건은 접수일로 바꾸지 않고 확인 요청을 반환한다.
  명시적 UI 범위와 질문 범위는 교집합으로 처리하며, 충돌하면 검색하지 않는다.
  잘못된 날짜·상대 날짜·분기·불분명한 여러 날짜·끝이 없는 범위는 확인 요청 대상이다.
- 합산·최신 유효 계약·환산·이익 추정 등은 이 경로에서 `unsupported`와 사유를 반환하며,
  질문 임베딩·검색·추출을 하지 않는다. 혼합 요청도 일부만 답하지 않는다.
  이 규칙은 일반 자연어 이해 모델이 아니므로 모든 표현의 거절/해석을 보장하지 않는다.
  일반적인 주의 문구만으로는 거절 시험을 통과시키지 않는다.
- 명시적 계약 필드 모드에만 적용한다. 일반 검색/진단 CLI의 기본 의미는 유지한다.
- 이 평가에서 실제로 실패한 항목을 다음 구현의 우선순위로 사용한다.
  이 파일을 테스트 통과용으로 느슨하게 바꾸거나, 여기서 자동으로 모델을 다시 선택하지 않는다.

## Windows 실행

프로젝트 루트의 `.env.perf`에 기존 `PERF_DATABASE_URL`과 `CLOVASTUDIO_API_KEY`가 있으면
PowerShell 변수를 다시 입력할 필요가 없다. 키/DB URL은 리포트에 기록하지 않는다.
기존 키 환경변수가 설정되어 있으면 파일보다 우선하므로 오래된 테스트 키에 주의한다.

API·DB 연결 없이 로컬 정답만 확인:

```powershell
python scripts/evaluate_contract_qa.py --dry-run
```

실제 40문항 평가:

```powershell
python scripts/evaluate_contract_qa.py `
  --benchmark-version v2 `
  --report data\quality\contract-qa-v2.json
```

정상적인 전체 실행에서 지원 대상 34문항만 질문 임베딩한다. 미지원 6문항은 0회다.
추가 확인 요청이나 오류가 생기면 호출 수는 줄고, 재시도 시 HTTP 호출은 추가될 수 있다.
문서 임베딩은 0회다. QPM 상한은 480이고 응답 헤더로 실제 한도에 맞춰 낮춘다.
직렬 실행하며 질문별 진행 상황을 출력한다. API 요청 timeout 30초/최대 재시도 1회,
SQL 문장별 timeout 20초를 둔다. 20초는 문장별 제한이지 전체 40문항 시간 보장은 아니다.
사용자의 기존 검색 시간에 따라 보통 수 분 규모가 예상되지만 실제 시간은 리포트로 확인한다.

DB 트랜잭션은 `READ ONLY`이며 프로세스가 쓰는 것은 새 JSON 리포트뿐이다.
기존 리포트는 덮어쓰지 않는다. 재실행 시 새 이름을 사용하며 기존 질문 호출을 캐시하지 않는다.
각 문항 후 완료분을 저장한다. Ctrl+C 또는 실행 오류 시 부분 결과를 남기고 중단한다.
오류 메시지에 포함될 수 있는 비밀정보를 피하려고 예외의 종류만 기록한다.

- 종료 코드 0: 40문항 완료 + 개발용 체크 전부 통과.
- 종료 코드 1: 40문항 완료했지만 품질 실패가 있음. 현재 미지원 기능 때문에 예상될 수 있다.
- 종료 코드 2: 설정/코퍼스 문제, 실행 중단/오류, 또는 `--limit`을 사용한 부분 실행.
- `status=completed`는 모든 질문의 평가가 끝났다는 뜻이지 모두 통과했다는 뜻이 아니다.
- `production_readiness_claim`은 항상 false다.
- `--limit 5`로 소규모 실행도 가능하지만, 전체 시험으로 승인되지 않는다.
- `--benchmark-version v1`은 원래 질문 그대로 **현재 코드**를 평가한다.
  이전 구현을 재현하는 옵션이 아니다. 결과 파일에는 반드시 새 이름을 쓴다.

결과를 읽을 때 Windows PowerShell은 UTF-8을 명시한다.

```powershell
$Qa = Get-Content data\quality\contract-qa-v2.json -Raw -Encoding UTF8 | ConvertFrom-Json
$Qa.summary | ConvertTo-Json -Depth 10
```
